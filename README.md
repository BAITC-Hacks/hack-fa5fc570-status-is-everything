# Samruk WindPilot AI

Прототип почасового прогноза нормализованной мощности двух турбин.
Исправленная версия использует проверяемый контракт погодных выпусков и отдельно оценивает модель «погода → мощность».

## Windows PowerShell

Python 3.12 (проверено):

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m src.train
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -m streamlit run app.py
```

Команды выполняются из корня репозитория. Также доступен run.bat.
Зависимости приложения закреплены в requirements.txt; полный проверенный набор — requirements-lock.txt.

## Что реализовано

- src/data.py: распознавание UTF-8/CP1251/UTF-16 и разделителя, обязательные поля, явное соответствие файлов турбинам.
- Отчёты отдельно по файлам: интервалы, пропуски, дубли, конфликты, диапазоны, подозрительные значения, полнота часов.
- Почасовые интервалы [HH:00, HH+1:00). Предположение: метка относится к началу 10-минутного интервала; настройка interval_end сдвигает её на 10 минут.
- Точные дубли учитываются один раз. Конфликтующее время исключается из средних и помечает час как непригодный для обучения. Пропущенные часы остаются строками с NaN. Нули и значения выше 1 сохраняются.
- Для средних нужны одновременно валидные три измеряемых поля и корректная 10-минутная сетка. По умолчанию обучение использует только полные часы (6 измерений).
- HistGradientBoostingRegressor отдельно для каждой турбины; только wind_speed и temperature. random_state=42, случайное внутреннее разбиение early_stopping отключено.
- Базовый метод: средняя мощность по диапазонам ветра шириной 0.5 м/с; неизвестный диапазон получает среднюю мощность обучения. Все значения рассчитаны только на обучении.
- Обучение до января 2026; проверка за январь. При ином покрытии выбирается последний целиком охваченный календарный месяц до февраля. Пропуски внутри месяца отражаются в числе часов проверки.
- Финальные модели переобучаются на всей допустимой истории строго до 2026-02-01.
- predict_power(weather_dataframe): контроль времён выпуска/доступности, будущих часов, дублей, конечности чисел и даты доступности обучающей истории.
- Агент выбирает последний доступный выпуск отдельно по турбинам, требует полные 24/48 часов, сохраняет версии прогнозов и журнал. При неизменных входах повторный расчёт не выполняется. Аудит всегда относится к новой версии.
- Дашборд показывает отдельные турбины, реальную проверку модели, качество данных и журнал. Автообновление опционально, каждые 30 секунд.

## Данные, настройки и результаты

config/settings.json — источник истины. Файлы явно сопоставлены turbine_1 и turbine_2 по именам.
CSV находятся в ВЭС/data/raw/. Исходные файлы не изменяются.
Пользователь подтвердил местное казахстанское время. Для указанной проектом Алматинской области выбран Asia/Almaty с историческими смещениями IANA.
Обучение использует местные часовые интервалы; при неоднозначном времени перехода на другой UTC offset соответствующие часы исключаются.
Шкала нормализации, паспортные ограничения, координаты и высота измерения ветра требуют подтверждения. МВт/МВт·ч, общий КИУМ и экономия не вычисляются.

Результаты:
- data/processed/hourly.csv
- reports/data_quality.json
- reports/metrics.json и validation_predictions.csv
- models/validated/turbine_1.joblib и turbine_2.joblib
- data/forecasts/ — версии прогнозов; reports/agent_events.jsonl — операции и ошибки.

Старые models/*.joblib, data/hourly_*.csv, data/weather_cache/*, data/february_* и копии в ВЭС/ сохранены как исторические артефакты, но исправленным приложением не используются.
Старые метрики, «90% интервалы», утверждения об экономии и физической мощности не подтверждены этим конвейером.

## Погода и автоматический пересчёт

### Предварительная оценка по Previous Runs

Во вкладке «Оценка за февраль» можно выбрать, например, 10 февраля 2026 года
и увидеть почасовую оценку мощности обеих турбин на 24 или 48 часов. Она
строится из Open-Meteo Previous Runs API, модель зафиксирована как
`gfs_seamless`, используются ветер на 100 м и температура на 2 м, запрос
явно задаёт `wind_speed_unit=ms` и `timezone=GMT`. Для каждой переменной
скачиваются `_previous_day1` и `_previous_day2`. В предварительном графике
выбирается ближайший фиксированный срез с номинальным lead time не меньше
расстояния от выбранного расчёта до прогнозируемого часа. День 0 и
бессуффиксные фактические значения не используются.

Источники координат для пробного запроса — ранее записанные значения в старой
версии `src/weather_service.py`: 43.645150, 78.535604 и 43.643198,
78.538828. Они не подтверждены как координаты оборудования и не перенесены
в рабочую конфигурацию. Обе точки Open-Meteo относит к одной ячейке
43.638138, 78.515625. Высота SCADA-ветра пока неизвестна.

```powershell
.\.venv\Scripts\python.exe -m src.previous_runs --start-date 2026-01-31 --end-date 2026-03-02 --turbine-1 43.645150 78.535604 --turbine-2 43.643198 78.538828
```

Для другого периода замените даты. Горизонт 48 часов у конца февраля требует
ещё и первые часы марта. Диагностический архив и отчёт сохраняются в
`data/weather/diagnostics/`; эти файлы не подаются в рабочий WeatherService.
API отдаёт значения, спрогнозированные за 24/48 часов до *каждого целевого
часа*, но не идентификатор полного модельного выпуска и не историческое
время его доступности. Поэтому `issued_at`/`available_at` не вычисляются
искусственно, а февральский replay по строгому контракту остаётся 0/28.
Для точного replay нужен архив отдельных выпусков и подтверждение их
исторической доступности. [Документация Previous Runs](https://open-meteo.com/en/docs/previous-runs-api),
[Single Runs](https://open-meteo.com/en/docs/single-runs-api).

Контракт источника и пример манифеста: config/WEATHER_INPUT.md.
Реального проверенного архива выпусков в репозитории нет. Поэтому запуск прогнозирования сейчас сообщает об отсутствии входа.
Старый Historical Forecast CSV не хранит issued_at/available_at; превращать его в допустимый архив добавлением выдуманных времён запрещено.
Fallback на реанализ и искусственное обновление ветра удалены.

Источник должен атомарно обновлять data/weather/forecasts.csv и source.json (временное несовпадение checksum приводит к отказу и повторной проверке).
Единицы m/s и degC обязательны; нужно документировать высоту прогноза и сопоставимость со SCADA.
Приложение доверяет предоставленным сведениям об источнике; checksum проверяет целостность, но не доказывает истинность метаданных.
Архивный источник ещё требуется подключить; монитор файла не загружает выпуски из интернета.

```powershell
.\.venv\Scripts\python.exe -m src.agent --origin "2026-02-01T00:00:00+05:00" --horizon 48
.\.venv\Scripts\python.exe -m src.agent --watch --interval 60
.\.venv\Scripts\python.exe -m src.backtest
```

Без --origin фоновый процесс использует текущий полный час. Новые реальные выпуски выбираются по issued_at и available_at <= текущему моменту расчёта.
С фиксированным --origin более поздние выпуски правильно отклоняются; для следующего расчёта нужно продвинуть origin.
valid_time обозначает начало прогнозируемого часа и строго больше forecast_origin; первые значения идут с origin+1h по origin+Hh.
Для origin 28 февраля, 48 часов нужны также мартовские часы.

## Ограничения оценки

Январские MAE/RMSE измеряют преобразование фактической погоды в мощность. Они НЕ являются качеством 24–48-часового прогноза.
Нужны одновременно архивные прогнозы погоды с доказуемой доступностью и фактическая мощность февраля для полноценной февральской оценки.
CSV, несмотря на названия, заканчиваются 31 января. Бэктест сообщает пропуски выпусков, не генерирует фиктивную точность и возвращает ненулевой код при неполном покрытии.
