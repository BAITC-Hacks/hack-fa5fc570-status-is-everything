# Samruk WindPilot AI

Решение кейса АО «Самрук-Қазына» на хакатоне HackAlem AI по почасовому прогнозированию выработки ветроэлектростанции (ВЭС) на горизонте 24–48 часов.

Система строит конвейер от сырых измерений SCADA двух ветротурбин до почасового прогноза мощности, с явным разделением на модель преобразования «погода → мощность» и контракт работы с архивными выпусками прогнозов погоды без заглядывания в будущее (*lookahead bias*).

---

## Быстрый старт

Проект протестирован на Python 3.12 и 3.13 (Windows / Linux).

```bash
# 1. Создание и активация виртуального окружения
python -m venv .venv
# Windows:
.\.venv\Scripts\activate
# Linux / macOS:
# source .venv/bin/activate

# 2. Установка зависимостей
pip install -r requirements.txt

# 3. Подготовка данных и валидация моделей
python -m src.train

# 4. Запуск тестов пайплайна
python -m unittest discover -s tests -v

# 5. Запуск веб-дашборда
streamlit run app.py
```

Также для Windows доступен готовый скрипт запуска: `run.bat`.

## Архитектура и принципы решения

Пайплайн спроектирован по модульному принципу с упором на воспроизводимость и прозрачность для эксплуатационных служб:

```
[SCADA 10-мин данные] ──► [src/data.py: почасовая агрегация + аудит качества]
                                  │
                                  ▼
[src/train.py] ──────────► [HistGradientBoostingRegressor по каждой турбине]
                                  │
                                  ▼ (валидация на январе 2026 против WindBinBaseline)
[Архивные прогнозы погоды] ──► [src/predict.py: проверка контракта (issued_at, available_at)]
                                  │
                                  ▼
[src/agent.py] ──────────► [Координатор: версионирование, аудит рисков, пересчёт]
                                  │
                                  ▼
[app.py] ────────────────► [Streamlit: визуализация, проверка модели, аудит данных]
```

### 1. Обработка сырых данных SCADA (`src/data.py`)
- **Исторический охват:** с 11 марта 2023 года по 31 января 2026 года (шаг 10 минут, 142 360 строк по Турбине 1 и 149 499 строк по Турбине 2).
- **Контроль целостности:** исходные файлы в `ВЭС/data/raw/` не модифицируются. Автоматически проверяются кодировка (UTF-8 / CP1251), разделители и соответствие столбцов.
- **Аудит пропусков:** алгоритм зафиксировал фактические эксплуатационные простои датчиков (максимальный разрыв в данных Турбины 1 составил 41 день 15 часов). Полнота пригодных для обучения часов на календарной сетке: 93.2% (Т1) и 97.6% (Т2).
- **Часовые пояса:** учтён официальный переход Республики Казахстан на единый часовой пояс `UTC+5` (в ночь на 1 марта 2024 года). Неоднозначные часы в момент перевода исключены из выборки обучения, что отражено в `reports/data_quality.json`.
- **Почасовая агрегация:** по умолчанию для расчета часового среднего требуются все 6 валидных 10-минутных замеров. Часы с пропусками остаются как `NaN` и не искажают обучающую выборку. Нулевые значения мощности сохранены (режим штиля или готовности).

### 2. Моделирование и валидация (`src/train.py`)
- **Модель:** `HistGradientBoostingRegressor` обучается независимо для каждой турбины на признаках скорости ветра и температуры окружающей среды (`random_state=42`, без скрытых стохастических эвристик).
- **Честный бейзлайн (`WindBinBaseline`):** расчет средней мощности по скользящим бинам скорости ветра шагом 0.5 м/с, построенный строго на обучающей части выборки.
- **Схема валидации:** временное отсечение (*temporal split*). Обучение строго до января 2026 года, оценка качества — на полном календарном январе 2026 года (744 часа).

**Результаты валидации на фактических данных января 2026 года:**

| Турбина | MAE модели | RMSE модели | MAE бейзлайна | RMSE бейзлайна | Часов проверки |
| :---: | :---: | :---: | :---: | :---: | :---: |
| **Турбина 1** | **0.0249** | **0.0483** | 0.0353 | 0.0584 | 744 ч (весь январь 2026) |
| **Турбина 2** | **0.0270** | **0.0642** | 0.0392 | 0.0729 | 744 ч (весь январь 2026) |

После фиксации метрик финальные модели переобучаются на всей доступной истории строго до 1 февраля 2026 года (23 666 и 24 784 часа). Данные февраля 2026 года в обучение не попадают.

## Контракт погодных данных и защита от «подглядывания в будущее»

Ключевое требование к промышленным системам прогнозирования — гарантия отсутствия *lookahead bias*. Модель в момент прогноза на дату $T$ обязана использовать только те метеопрогнозы, которые фактически были опубликованы и доступны до момента $T$.

Спецификация описана в `config/WEATHER_INPUT.md`:
* **Обязательные поля:** `turbine_id`, `issued_at` (время выпуска прогона численной модели), `available_at` (время фактической доступности прогноза потребителю), `valid_time` (начало прогнозируемого часового интервала), `wind_speed`, `temperature`.
* **Правило темпоральной доступности:** `issued_at <= forecast_origin` и `available_at <= forecast_origin`.
* **Целостность:** файл `data/weather/forecasts.csv` верифицируется контрольной суммой SHA-256 через манифест `data/weather/source.json`.
* Синтетическая генерация шума и подстановка фактических данных задним числом (reanalysis) исключены на уровне валидатора `src/predict.py`.

### Предварительная оценка по Open-Meteo Previous Runs API (`src/previous_runs.py`)

Для демонстрации прогноза на февраль 2026 года без заглядывания в будущее реализован модуль `src/previous_runs.py`, использующий официальный [Open-Meteo Previous Runs API](https://open-meteo.com/en/docs/previous-runs-api).
* Модель: `gfs_seamless`, параметры: скорость ветра на 100 м (`wind_speed_unit=ms`) и температура на 2 м (`temperature_2m`).
* Запрашиваются фиксированные срезы с опережением: `_previous_day1` (lead time 24 ч) и `_previous_day2` (lead time 48 ч). День 0 (текущие фактические данные) исключён.
* Запуск загрузки диагностического среза:
```bash
python -m src.previous_runs --start-date 2026-01-31 --end-date 2026-03-02 --turbine-1 43.645150 78.535604 --turbine-2 43.643198 78.538828
```
Диагностический архив и отчёт сохраняются в `data/weather/diagnostics/`. Так как Previous Runs API отдаёт значения, спрогнозированные с фиксированным lead time к каждому часу, но не публикует точное системное время выпуска и доступности прогона, эти данные служат проверенной демонстрацией среза, сохраняя строгий контракт для боевого режима.

### Работа агента в режиме мониторинга (`src/agent.py`)
Координатор поддерживает запуск через CLI:
```bash
# Разовый расчёт на конкретную дату и горизонт (24 или 48 часов):
python -m src.agent --origin "2026-02-01T00:00:00+05:00" --horizon 48

# Фоновый мониторинг появления новых выпусков погоды (пересчёт по событию):
python -m src.agent --watch --interval 60

# Запуск сценарного бэктеста:
python -m src.backtest
```
При неизменных входных данных повторный расчёт не выполняется — агент версионирует состояние через хеширование входов и настроек, сохраняя журнал операций в `reports/agent_events.jsonl`.

## Честный скоуп и границы применимости

1. **Единицы измерения:** В предоставленных организаторами CSV активная мощность приведена как *«Нормализованная активная мощность»* в диапазоне $[0.0 \dots 1.0]$. В коде не навязывается искусственный перевод в мегаватты или тенге, поскольку паспортная мощность конкретных турбин и коммерческие параметры в исходных данных не заданы.
2. **Смысл метрик января 2026:** Приведённые MAE (0.025 и 0.027) оценивают качество аппроксимации функции $f(\text{ветер}, \text{температура}) \to \text{мощность}$ на реальных датчиках. Это необходимое базовое условие, но это не оценка сквозного 24–48-часового прогноза погоды.
3. **Февральский бэктест:** Для полноценной верификации точности за февраль 2026 года требуется подключение сертифицированного архива прогонов метеомоделей с метками доступности (`available_at`) и фактические измерения SCADA за февраль для сверки.
